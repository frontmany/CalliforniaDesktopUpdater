# Как апдейтер применяет обновление

## Цепочка

1. Клиент (CalliforniaDesktop, `UpdateService`) находит новую версию, качает
   изменившиеся файлы по манифесту в
   `%LOCALAPPDATA%\Callifornia\updates\staging\<version>\`.
2. Копирует `updater.exe` из папки установки в
   `%LOCALAPPDATA%\Callifornia\updates\bin\` (папку, которую предстоит
   обновлять, запускать нельзя), запускает его с `apply` и штатно выходит.
3. Апдейтер ждёт выхода по PID и по эксклюзивной пробе `Callifornia.exe`,
   проверяет манифест, подменяет файлы и перезапускает клиент.

Манифесты отдаёт сервис Updates бэкенда, блобы файлов клиент берёт с
`/v1/updates/files/<sha256>`. Публикует релиз `ci/release/publish-release.mjs`
клиента: подписывает манифест, заливает блобы.

## Свойства

- **Ноль зависимостей на рантайме.** Апдейтер подменяет DLL рядом с собой,
  поэтому сам от них не зависит: без Qt и OpenSSL, статический CRT (`/MT`),
  SHA-256 через Windows CNG (bcrypt), Ed25519 из вендоренного orlp/ed25519
  (только проверка), JSON из nlohmann single-header.
- **Подпись прежде всего.** До любых действий проверяется Ed25519-подпись
  `manifest.json` вшитым публичным ключом (`src/public_key.hpp`, его делает
  `ci/release/generate-update-keys.mjs` клиента).
- **Атомарная подмена с журналом.** Файлы из staging копируются в
  `<install>\.update\incoming\`, после чего подмена это только переименования
  на одном томе (атомарно на NTFS). Журнал `.update\journal.json` и запись
  RunOnce позволяют докатить обновление после сбоя или перезагрузки
  (`repair`).
- **Откат.** Если подмена упала (файл заблокирован и т.п.), всё
  восстанавливается из `.update\backup\` и запускается прежняя версия. Если и
  `repair` не может докатить, он тоже откатывается и запускает прежнюю версию,
  а не оставляет журнал, из-за которого клиент перестал бы стартовать.
- **Не зависает никогда.** На весь запуск бюджет 10 минут. Когда он кончился,
  апдейтер пишет, на каком шаге стоял, поднимает приложение и убивает себя
  (`TerminateProcess`, код 9). Повторы файловых операций тратят тот же бюджет
  и оставляют запас на откат.
- **Ждёт каждый файл.** Перед подменой каждый затрагиваемый файл получает до
  30 с, чтобы его отпустили (не только `Callifornia.exe`). Кто держит файл,
  спрашивается у Restart Manager и пишется в лог. Без этого ожидания терялись
  обновления, перепрыгивающие через релиз.
- **Без окон.** Подсистема WIN32, каждый шаг в логе строкой `phase:`, итог в
  `last-apply.json` (`status`, `version`, `phase`, `detail`), клиент
  показывает его человеку.

## Взаимоисключение

Пока апдейтер работает, он держит именованный мьютекс
`Local\CalliforniaUpdaterApplying`. Клиент проверяет его при старте и молча
выходит, если идёт обновление. Имя мьютекса это договор двух бинарников, его
не переименовывать.

## Коды выхода

| Код | Значение |
|---|---|
| 0 | применено |
| 2 | неверные аргументы или уже работает другой апдейтер |
| 3 | приложение не вышло |
| 4 | подпись или хэш не сошлись |
| 5 | нет прав на запись |
| 6 | подмена упала, откат успешен |
| 7 | подмена и откат упали, журнал оставлен для `repair` |
| 8 | `repair`: делать нечего |
| 9 | бюджет запуска исчерпан, процесс убит сторожевым таймером |

## Тесты

`updater_tests` проверяет части по отдельности. `scripts/integration-test.ps1`
собирает фальшивую установку и подписанное обновление во временных папках,
гоняет `apply` и проверяет подмену, манифест и уборку; последний сценарий
держит файл открытым дольше, чем переживает один только повтор
переименования. Ключ для подписи нужен парный вшитому: другой ключ даёт код 4
и строку `manifest signature verification failed`, ровно как сломанный
апдейтер.
